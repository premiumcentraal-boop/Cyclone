## 2. How a change reaches the ledger (and why nothing is missed)

1. **Source tables.** Triggers on `account`, `task`, `run`, `approval` and `phone_health` write an **outbox** row in the
   same statement as every insert, update or delete. This covers every write site in every module, including ones
   written before the ledger existed, with no change to their code.
2. **The drain.** `Ledger.drain()` turns the outbox into a `<kind>.changed` snapshot event. It appends only when the
   snapshot differs from the subject's projection, so a heartbeat that changes nothing makes no event. It runs after
   every audited action, at the end of every engine tick, and before every read.
3. **The audit chain.** Every entry is also appended as `audit.recorded`, with its detail reduced to plain values and
   secret-looking text withheld.
4. **A crash before a drain** leaves the outbox rows. The next start drains them (tested).
5. **One malformed row** is skipped and recorded in `skipped`, never allowed to block later changes (tested).
6. **Phones are recorded coarsely:** battery to its tenth, storage in whole GB. A phone's battery changes every minute;
   fine-grained health is a time series in stage 7, not a stream of events. This keeps 1,000 phones well inside the
   D8 budget of 1,000,000 events a day.

## 5. Decisions taken in this run

| # | Decision | Why |
|---|---|---|
| S1-1 | Changes reach the ledger through **triggers and an outbox**, not by editing each write site. | Phone health is written in 8 places and approvals in 7, across several modules. Triggers catch them all, in the same statement as the change. |
| S1-2 | State is recorded as **snapshots**, appended only when they differ from the projection. | Replay is exact, and a repeated heartbeat or poll makes no event. |
| S1-3 | `audit.recorded` keeps a **reduced detail**: plain values under plain keys; nested objects are dropped; secret-looking text is withheld. | The audit detail was never typed. The ledger must stay typed and safe without breaking any existing audit call. |
| S1-4 | The store **joins** a transaction an older module opened (the vault's restore) as a savepoint, instead of refusing. | The ledger appends inside such a transaction; its events then commit or roll back with it. |
| S1-5 | A domain write and its event are **not yet one transaction**. The outbox makes the event certain, but it may land up to one tick later. | Making them one transaction means moving each module's writes into the store, which the SQL ratchet tracks module by module. |

## 6. Risks accepted

- **Write cost.** Audited writes take about twice as long, still under a millisecond each.
- **File growth.** About 0.65 KB per event. 1,000,000 events a day is about 650 MB a day at full D8 load. Stage 14 sets
  retention and compaction for the payloads; the hash chain stays whole.
- **Whole-chain verification** is linear. It is fine at today's size and needs to become incremental by stage 14.
